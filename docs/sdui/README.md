## 当前结论

- 终端脚本和接入设计已经给出了大部分有效契约，Binary、握手、消息判别和基础能力无需重复确认。
- 平台 v2 主体代码已经存在，但多处按历史平台假设实现，与终端样例并不兼容；这些属于平台待改造，不是终端待确认。
- 正式开发前只需裁决协议版本、Schema 形态、业务配置模型和音频异常结束四组冲突，并补齐图片/Canvas、scenes Schema 和生产认证中实际需要的输入。
- “代码已实现”不等于“契约已对齐”或“端到端已交付”。当前首先完成 [端云契约](TERMINAL_CONTRACT.md) 的 C1–C4 裁决。
- 旧协议和旧 Section 体系仍在代码中。真实设备完成 v2 回归前不得删除；确认切换后按 [交付台账](DELIVERY_CHECKLIST.md) 的清理门禁执行。

## 使用顺序

1. 平台开发先读《平台重构指南》，只在目标边界内改造。
2. 任何涉及字段、消息名、字节序、容量或错误码的判断，先查《端云契约》；标为 `待确认` 的内容不得当成终端事实。
3. 开工和合并前更新《交付台账》，状态必须附代码、测试或联调证据。
4. 真实终端给出结论后，直接回填《端云契约》，同步更新《交付台账》，不再新建会议纪要式规范。

## 文档规则

- 活跃 Markdown 始终不超过 4 份；新内容必须归入现有职责，不新增平行文档。
- 状态只用：`已实现`、`部分实现`、`待实现`、`阻塞`、`延期清理`、`已验收`。
- `已实现` 表示平台代码和聚焦测试存在；`已验收` 才表示真实终端端到端通过。
- 设计假设必须带确认编号 `Txx`；禁止在多个文档复制同一待确认清单。
- Swagger 和代码控制器是 HTTP 端点明细来源；本文档只维护稳定边界和闭环，不复制易漂移的完整接口表。
- 历史稿只归档、不继续修改。需要恢复历史结论时，先在活跃文档中重新核对代码和终端事实。
