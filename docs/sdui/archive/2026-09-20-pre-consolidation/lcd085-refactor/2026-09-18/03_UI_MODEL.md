# LCD_085 UI 模型

## 1. 产品边界

UI 只服务 128×128、无触摸、使用有限物理按键的 LCD_085，不兼容其他屏幕或产品形态。

同一时间只存在一个平台主视图：

```text
LCD_085 主视图
├── 单 Section
├── 全屏图片
└── Matrix Canvas
```

三种主视图互斥，新的主视图完整替换旧主视图。终端不组合多个 Section，不混合 Section、图片和 Canvas，也不维护通用页面栈。

系统界面只存在于业务接入前或业务不可用阶段，包括启动、配网、设备注册、等待平台以及平台/网络被确认断开。进入业务后平台独占主视图，系统不得以浮层、弹窗或页面替换方式侵入业务显示。

录音、播放、普通错误和设备状态不触发系统 UI，必要反馈使用提示音、RGB 或平台 UI。短暂网络抖动不立即抢占屏幕；确认断开后系统界面可以接管，但业务主视图仍保留在内存中，连接恢复后重新显示，除非平台下发新的主视图或执行 `business.reset`。

## 2. 单 Section 模式

平台每次下发一个完整 Section，由该 Section 独占整个屏幕。

不再支持：

- 多 Section 纵向或横向拼接；
- Section 嵌套；
- 通用栅格和自由布局；
- `vertical_scroll`、`horizontal_pages` 等多内容布局；
- large/compact 等跨屏幕适配模式；
- 面向触摸的点击、手势和控件状态；
- Section 级增删改 Patch。

Section 更新采用完整替换。菜单内部的项目列表和焦点移动属于单个 Section 的固定能力，不构成多 Section 页面。

### 2.1 目标 Section 类型

当前收敛为以下类型：

| 类型 | 用途 | 主要边界 |
|---|---|---|
| `status_section` | 标题、主数值、简短说明和可选进度 | 固定布局，不提供自由组合 |
| `metrics_section` | 少量指标概览 | 固定最多 2～4 项，每项为标签、数值和可选单位 |
| `text_section` | 短消息和说明 | 限制文本长度和行数，不支持富文本 |
| `menu_section` | 物理按键菜单 | 上下移动焦点、确认和可选返回，项目可关联平台 token |
| `chart_section` | 小型趋势图 | 单序列、有限数据点、无触摸缩放和数据点交互 |

`chart_section` 保留，但只负责风格固定、成本可控的简单图表。复杂图表由平台渲染成全屏图片。

现有 `hero_section`、`progress_section` 等能力是否合并进入 `status_section`，以及每类 Section 的准确字段和限制，在 Section Schema 设计时确定。目标是减少类型和属性，而不是直接继承当前字段全集。

## 3. 全屏图片模式

平台可以下发适配 LCD_085 的完整图片，终端绕过 Section 布局直接显示。该模式适用于二维码、海报、仪表盘快照、平台生成卡片和其他固定 Section 难以表达的视觉内容。

首期按全屏内容设计，不增加任意坐标的局部图片覆盖能力，避免重新引入图层、坐标和增量合成模型。

图片可以使用调色板索引矩阵表示。平台随图片下发完整调色板，调色板项目使用 RGB565：

```text
0 → RGB565 颜色值
1 → RGB565 颜色值
2 → RGB565 颜色值
...
```

终端不预置或解释调色板语义，只使用颜色编号查表渲染。

## 4. Matrix Canvas 模式

Matrix Canvas 将屏幕抽象为低色域的二维颜色索引数组，平台可以连续推送帧，用于像素画板、低帧率动画、动态表情和简单实时图形。

Canvas 会话开始时，平台完整提供：

- 逻辑宽度和高度；
- 完整 RGB565 调色板；
- 与调色板大小对应的索引位数；
- 后续帧解释所需的必要参数。

后续帧只传输紧凑的颜色索引矩阵。会话期间不增量修改调色板；需要更换调色板时重新开始 Canvas。

### 4.1 逻辑分辨率

Canvas 不要求始终使用 128×128。首期优先支持可整数放大到物理屏幕的方形分辨率：

```text
16×16   → 8 倍最近邻放大
32×32   → 4 倍最近邻放大
64×64   → 2 倍最近邻放大
128×128 → 原始分辨率
```

不进行插值、抗锯齿或复杂缩放。

### 4.2 色域与数据量

首期面向 2、4 或 16 色场景：

```text
2 色  → 1 bit/pixel
4 色  → 2 bit/pixel
16 色 → 4 bit/pixel
```

例如 32×32、16 色的一帧像素数据约为 512 Byte；128×128、16 色约为 8 KB。完整调色板最多只占少量额外字节。

### 4.3 运行边界

- Canvas 按完整帧更新，不提供逐像素网络命令；
- 新帧替换旧帧，不维护历史帧；
- 消费速度不足时不能无限排队，应优先保留最新帧；
- 新的 Section、图片或业务 reset 会结束当前 Canvas；
- Canvas 传输不得阻塞控制消息和音频数据；
- 分辨率、调色板和像素数据必须满足终端声明的上限。

## 5. 图片与 Canvas 的共用关系

图片和 Canvas 可以共用调色板解析、索引矩阵校验、缩放和 framebuffer 写入能力：

```text
全屏图片 = 接收一个矩阵并持续显示
Canvas    = 在一个会话中连续接收多个矩阵
```

二者的产品语义和生命周期保持独立，不能因为底层复用而合并成含义模糊的通用 UI 消息。

## 6. 留到协议阶段讨论

以下内容不在当前 UI 模型中提前固定：

- JSON 控制消息与二进制数据的关联方式；
- 单条二进制消息的最大尺寸；
- 图片或帧是否需要应用层分片；
- 大文件的 `begin/chunk/end` 生命周期；
- 帧序号、丢帧检测和流控方式；
- 图片、Canvas、音频和资源数据是否共用底层二进制封装；
- RGB565 全色图片、字体及其他较大资源的传输方式；
- 未完成图片等有界对象在断线后从头重新传输的具体流程。

协议设计必须保证缓存、队列和重组数据都有明确上限，不能因大数据传输造成 OOM、无界积压或控制消息饥饿。

## 7. 后续需要明确

- `status_section` 是否需要终端本地计时能力，或只展示平台给出的静态时间值；
- 五类 Section 的最终字段、长度、数量和取值限制；
- `chart_section` 的图表形式和最大数据点数量；
- `menu_section` 的物理按键映射和返回行为；
- Canvas 首期实际需要支持的最大分辨率、色数和帧率。
