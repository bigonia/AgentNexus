# 终端对接待确认清单

> **唯一维护位置**。T1–T16 的权威登记处是本文档；`11_FEATURE_MATRIX.md §8`、`10_PLATFORM_UPGRADE.md §11`、`12_DESIGN_NOTES.md §5` 只做引用，不再各自维护副本。
>
> 维护者：平台侧。更新时机：每次与终端确认后。
> 建表日期：2026-09-20 ｜ 对应平台版本：0.14.2

## 1. 怎么用

1. **按批次谈，不要按条谈。** §2 把 16 项聚成 5 批，同批内的问题互相牵连，分开确认会出现"各自都说对、合起来对不上"。
2. **每项都带平台侧当前假设。** 和终端确认时不用问开放问题，直接念假设让对方核对——假设是从代码里抄的，不是设想的。
3. **确认结果写回 §3 对应项**，并把状态位从 `待确认` 改为 `已答复`。
4. **通知平台侧。** 在对话里直接说编号加结论即可（例如「T3 确认：magic 用 0x414E，长度字段改大端」）。平台侧据此执行该项「假设不成立时的动作」列，改完把状态位改为 `已落地`。

状态图例：`待确认` ｜ `已答复`（终端给了结论，平台待落地）｜ `已落地`（平台已改完并测试通过）｜ `终端未采纳`（终端拒绝该假设，需另议方案）

**确认时最值得带回来的三件事**（缺一则平台可能要追问）：
- 终端实际采用的字段名 / 字节序 / 取值，逐字或逐字节；
- 该实现是「已定稿」还是「暂时这样、后续会改」；
- 若与平台假设不同，终端是否愿意改（有些项改平台更便宜）。

## 2. 建议的确认批次

批次划分依据是**耦合**，不是重要性：同批内任一项不一致都会让整批无法联调。

| 批次 | 主题 | 包含项 | 为什么必须一起定 |
| --- | --- | --- | --- |
| A | 连接层（最小可联通集） | T1、T2、T3、T5 | 这四项任一不一致，设备**根本连不上**；是终端固件最早需要跑通的部分 |
| B | 二进制载荷 | T7、T8、T12 | T7 与 T12 是同一份编码的两半（颜色表示 / 位序），分开定必然对不上 |
| C | 业务配置与交互 | T4、T13、T14、T15 | T13 与 T15 是同一件事的两面（终端能不能执行平台指定的动作），T4/T14 决定 token 怎么落进配置、怎么带回来 |
| D | 音频链路 | T9、T11、T16 | 同一条链路的宣告、消息名、载荷容器，分开定会出现「能收不能停」 |
| E | 独立项 | T6、T10 | 不与其它项耦合，可单独谈 |

**建议节奏**：批次 A 谈完即可开始终端侧联调（平台侧无阻塞）；批次 B/C 是功能能否闭环的关键；批次 D 影响录音这一条平台目前**没有替代通路**的链路（见 T11）。

## 3. 逐项详情

### 批次 A｜连接层

#### T1 握手字段承载位置

- **问终端**：`device_id`、`protocol_version`、`capability_hash` 放在 WebSocket 连接参数里，还是放在首条 `device.hello` 请求的 body 里？
- **对应缺口**：G1
- **平台当前假设**：**两者都支持**，优先取连接参数，缺失则回落到首条 `device.hello`；两者都缺则拒绝绑定。实现见 `sdui/v2/transport/SduiV2WebSocketHandler`（连接参数键 `deviceId` / `protocolVersion`，兼容下划线别名 `protocol_version`；hello body 同名字段）。非 hello 的首条消息会被忽略并告警。
- **阻塞**：1.10
- **假设不成立时的动作**：低代价。容器类 `DeviceHandshake` 允许任一字段为 null，改的是取值优先级，不动协议内核。
- **确认结果**：（待填）

#### T2 `capability_hash` 算法与编码

- **问终端**：hash 用什么算法、什么编码、取多少位？输入是原始 Schema JSON 还是某种规范化形式？
- **对应缺口**：G10
- **平台当前假设**：**规范化 JSON（对象键字典序排序、剔除 null 字段、数组保持原序）→ UTF-8 字节 → SHA-256 → 十六进制小写前 16 字符**。实现见 `sdui/v2/capability/CapabilityHash`，`HASH_LENGTH = 16`；不变量是「**数组顺序有语义**」（如 `params` 声明顺序），故不排序数组。
- **阻塞**：2.2、2.4
- **假设不成立时的动作**：**高代价（但可控）**。算法与终端不一致不会导致功能错误——只会让每次连接都判定为「hash 不匹配」并触发全量 Schema 同步，即**退化为性能问题而非正确性问题**。因此可以「先按现有假设联调，跑通后再对齐」。改法是替换 `CapabilityHash` 单类。
- **确认结果**：（待填）

#### T3 二进制帧头字节布局与 `dataType` 取值

- **问终端**：帧头几个字节、字段顺序、各字段字节序、magic 用什么；`dataType` 的取值域。
- **对应缺口**：G2、G3
- **平台当前假设**：**8 字节头**——

  | 偏移 | 长度 | 字段 | 平台取值 |
  | --- | --- | --- | --- |
  | 0 | 2B | magic | `0x414E`（`'A' 'N'`） |
  | 2 | 1B | version | `2` |
  | 3 | 1B | dataType | 见下 |
  | 4 | 4B | length（payload 字节数） | **小端** |
  | 8 | N | payload | — |

  `dataType` 取值：`1` 音频（双向）、`2` 全屏图片、`3` Canvas 单帧、`4` 能力 Schema（终端→平台）、`5` 其它资源（字体等）。实现见 `sdui/v2/protocol/BinaryFrameCodecV2` 与 `BinaryDataType`。
  **头里没有**序号、CRC、长度校验字段——旧协议的 16 字节头（magic `0x5344`）会被明确拒绝并报 `legacy binary frame is not accepted on the v2 channel`。
  首期以「同类数据不并发」约束时序，因此**不设** `stream_id` / `transfer_id`。
- **阻塞**：1.5、4.3、4.5、4.8
- **假设不成立时的动作**：**高代价**——帧头是四种二进制通道（音频 / 图片 / Canvas / Schema）的共同前置，字节序或字段序不一致会让全部二进制通道同时失效。改法集中在 `BinaryFrameCodecV2` 单类，但需要与 T7/T12 一起回归。
- **附**：单帧 payload 上限 8192 字节（可配置，G4），见 T8。
- **确认结果**：（待填）

#### T5 错误码最小集合

- **问终端**：终端会报哪些错误名？是否与平台集合兼容？未识别错误名时的兜底行为？
- **对应缺口**：G5
- **平台当前假设**：13 个错误名 + 2 个结束原因，见 `sdui/v2/protocol/ProtocolErrors`：

  `invalid_envelope`、`unknown_name`、`not_connected`、`business_not_active`、`binding_not_found`、`config_invalid`、`invalid_value`、`resource_exhausted`、`queue_full`、`frame_too_large`、`audio_busy`、`no_active_stream`、`unsupported`、`timeout`；
  结束原因：`buffer_full`、`playback_timeout`。
- **阻塞**：3.4、4.15、全部失败路径
- **假设不成立时的动作**：低代价（改常量），但**语义要对齐**——重点是 `resource_exhausted` 在「能力尚未同步完成」时是否复用（平台目前复用），以及 `unsupported` 与 `unknown_name` 的分工（平台约定：名字不认识用后者，名字认识但不支持用前者）。
- **确认结果**：（待填）

### 批次 B｜二进制载荷

#### T7 图片调色板与索引矩阵编码

- **问终端**：调色板每项几字节、字节序？索引矩阵是紧凑打包还是每像素一字节？位序？
- **对应缺口**：G20
- **平台当前假设**：
  - **调色板**：每项 2 字节，**大端序 RGB565**，顺序即索引 `0..N-1`；
  - **索引矩阵**：按 `ceil(log2(paletteSize))` **位紧凑打包**，**行优先**，**字节内低位在前**（LSB first）；
  - 索引位宽按调色板大小取 `1 / 2 / 4 / 8` 位；首期只支持 ≤16 色，超过报 `unsupported`。

  实现见 `sdui/v2/display/PaletteImageCodec`。
- **阻塞**：4.3
- **假设不成立时的动作**：**高代价**——这是平台自认风险最高的假设之一（源码注释原文：「必须与终端实现对齐后才能用于真实设备」）。改法集中在 `PaletteImageCodec`，但解包逻辑（`unpack`）是校验与自检的基准，改错会让「发送成功」与「显示正确」脱钩。
- **确认结果**：（待填）

#### T12 调色板与索引矩阵的承载通道及位序

- **问终端**：调色板随 `display.image.begin` 的 JSON 下发可以吗？还是要求单独走二进制通道？索引矩阵走 `dataType=2` 的二进制帧可以吗？
- **对应缺口**：G20、G2
- **平台当前假设**：**调色板走 `display.image.begin` 的 JSON body**，字段 `width` / `height` / `paletteSize` / `paletteRgb565`（int 数组）/ `totalBytes`；**索引矩阵走 `dataType=2` 的二进制帧**。Canvas 开场的 `display.canvas.open` 结构相同，多一个可选 `maxFps`。依据：`03_UI_MODEL.md §4.2` 明确「完整调色板最多只占少量额外字节」，故不单独走二进制通道。位序同 T7。
- **阻塞**：4.3、4.5
- **假设不成立时的动作**：中高代价。承载通道改到二进制需要新增一个 `dataType` 并调整开场时序（调色板必须早于像素到达），会波及 `DisplayCommandService` 与终端侧解析顺序。**与 T7 必须同批确认。**
- **确认结果**：（待填）

#### T8 Canvas 分辨率、色数、帧率上限

- **问终端**：Canvas 支持的最大分辨率、色数、帧率分别是多少？超限时终端是拒绝还是降级？
- **对应缺口**：G4
- **平台当前假设**：**平台侧没有独立的 Canvas 上限声明**，只受两个通用约束：单帧 payload ≤ 8192 字节、Canvas 待发帧队列深度固定为 1（只保留最新帧，旧帧丢弃）。`display.canvas.open` 会带上 `maxFps`，但这是平台**向终端提出**的值，不是平台已知的终端上限。配置见 `sdui/v2/V2ProtocolProperties`，默认值同步写在 `application.yml`。
- **阻塞**：4.5
- **假设不成立时的动作**：**这是纯缺口，不是待核对项**——平台目前无法预判一帧会不会超限，只能依赖终端返回 `frame_too_large`。终端给出上限后，平台应在生成侧提前校验并给出明确错误，而不是让设备端拒绝。需要新增实现，不是改假设。
- **确认结果**：（待填）

### 批次 C｜业务配置与交互

#### T4 业务配置 JSON 结构与上限

- **问终端**：`business.update` 的 body 字段名与嵌套结构；配置体积上限；能否接受「完整快照 + 原子替换」的语义？
- **对应缺口**：G13、G16
- **平台当前假设**：body **不含 `deviceId`**（设备标识不重复携带），结构为

  ```
  { configVersion: <long>,
    triggers: [ { triggerId, source, token?, responses: [ { action, params? } ] } ] }
  ```

  `params` 为空时省略。平台侧上限：单配置绑定数 ≤ 32、单绑定响应数 ≤ 8、token ≤ 48 字节。`configVersion` 由平台自增，**平台假设终端原样保存但不回显**，故平台只用它做本地漂移检测与日志关联，不作协议确认依据。实现见 `sdui/v2/business/BusinessConfig`、`TriggerBinding#toWire`、`ResponseStep#toWire`。
- **阻塞**：3.1、3.3
- **假设不成立时的动作**：中代价。字段名可改（`toWire` 单点）；**若终端要求回显 `configVersion`**，则为新增能力，平台可据此补上「部署是否真正生效」的判定——这是目前平台用「组装校验 + 下发校验干跑」替代的部分。
- **确认结果**：（待填）

#### T13 本地响应动作的名称与参数集合

- **问终端**：终端本地响应序列里可用的**动作名全集**与每个动作的参数集合是什么？
- **对应缺口**：无缺口编号，属模型未定义。
- **平台当前假设**：**平台只知道一个动作名**——`platform.interaction.report`（含义是「本步执行完，把交互交回平台」，参数为空）。其余动作名平台**不知道，也无法猜**。`ResponseStep` 只约束「动作名必须出现在能力 Schema 的 `actions` 中且该项 `usableIn=binding`」，不硬编码任何具体动作。
- **阻塞**：5.1.1（`WorkflowActionMapper` 的节点映射表无法定稿）
- **假设不成立时的动作**：**这不是「假设可能有偏差」，而是「缺输入」**。终端给出动作名全集后，平台需要新增映射表把工作流节点翻译成这些动作；在拿到之前，工作流节点只能有两种落法——要么走 `platform.interaction.report` 回平台（网络往返，违背重构目标），要么不闭环。**建议优先确认本项**，它是工作流下沉能力的天花板。
- **确认结果**：（待填）

#### T14 终端上报交互结果时携带的 token 字段名与位置

- **问终端**：`platform.interaction.report` 上报时，token 放在 body 的哪个字段？`device_id` 是否随报（平台从连接取）？
- **对应缺口**：无缺口编号。
- **平台当前假设**：**token 是 body 的顶层字段 `token`**；`deviceId` **不要求终端携带**，平台从连接上下文取。平台侧据此查绑定表（只匹配「平台签发的绑定」，即 `source` 为平台触发的项）并恢复业务上下文。`triggerId` 与 `contextRef` 都由平台在签发 token 时写入，**终端不感知、不回传**。实现见 `sdui/v2/business/BusinessInteraction`。
- **阻塞**：5.1.3、5.5
- **假设不成立时的动作**：中代价，改法集中在 `BusinessInteraction` 的解析处与 `InteractionTokenService` 的签发内容。注意 token 是**不透明**的（终端不应解析其内容），只要确认传输位置即可。
- **确认结果**：（待填）

#### T15 平台能否为动态节点签发专用绑定 / 新 token（G25）

- **问终端**：终端能否接受「平台为一个动态节点生成专用绑定并签发 token」这种形态？绑定的载体是什么（新增绑定项 / 复用已有项 / 其它）？
- **对应缺口**：G25
- **平台当前假设**：**平台当前没有这个能力**，实现上如实返回 `terminal_action_required`（见 `WorkflowPlatformStepExecutor.STATUS_TERMINAL_ACTION_REQUIRED`），**不退化成旧协议的遥控路径**。原因：`rgb.effect` / `audio.record` 这类动作在能力 Schema 里只声明 `usableIn=binding`，平台没有任何请求可发给它，所以平台无法自己发起。
- **阻塞**：5.6.1、5.7、5.7.1
- **假设不成立时的动作**：**属新增能力**。若终端不支持，代价是「这类节点的动作必须由终端本地序列驱动，平台只能等待」，即该类节点不闭环——平台已选择接受这个代价（见 `12_DESIGN_NOTES.md §4.12` 的裁决记录）。**与 T13 同批确认**：T13 给动作名全集，T15 决定这些动作能否被平台按需驱动。
- **确认结果**：（待填）

### 批次 D｜音频链路

#### T9 音频开始 / 结束 / 异常消息的名称与超时值

- **问终端**：三种消息的准确拼写；结束与异常是否是两个不同消息？超时值由谁定？
- **对应缺口**：G4、G18
- **平台当前假设**：消息名 **`audio.start` / `audio.stop` / `audio.abort`**，`audio.abort` 带原因字段（平台已知原因：`buffer_full`、`playback_timeout`）。平台侧接收超时默认 **15000 ms**（可配置 `sdui.v2.audio-receive-timeout-ms`），超时后由平台判定异常终止——即**同一异常，终端与平台各有一个超时源**，哪个先触发都会成立。实现见 `V2Names`、`AudioStreamService`、`ProtocolErrors`。
- **阻塞**：4.8、4.11
- **假设不成立时的动作**：低代价（改常量）。需要留意的是**超时归属**：平台侧超时扫的是「持续无数据」，终端侧是「缓冲满」，两者语义不同，确认时应问清终端是否也会主动报超时。
- **确认结果**：（待填）

#### T11 上行音频流的开始宣告方式

- **问终端**：录音开始时终端如何告知平台？是否有独立的开始消息，还是复用 `audio.start` 并带方向字段？
- **对应缺口**：G18
- **平台当前假设**：**终端发 `audio.start` 事件，平台读其 `direction` 字段**——值为 `downlink` 时判定为下行（平台在播），**其它值或缺失时判定为上行**（终端在录）。实现见 `sdui/v2/transport/sink/AudioLifecycleEventSink`。
- **阻塞**：4.9、4.11
- **假设不成立时的动作**：中低代价，改 `AudioLifecycleEventSink` 的方向判定。**但本项的真正风险不在字段名**：旧协议的上行音频链路（`AudioRecordHandler` 等）是平台**唯一**的录音通路，v2 侧平台虽已实现接收状态机，但**端到端录音尚未在真实设备上验证过**（见 §4 的最小联通集之外）。在 T11 定稿并验证之前，旧录音链路不能删。
- **确认结果**：（待填）

#### T16 下行音频的容器约定

- **问终端**：终端接收的音频帧期望裸 PCM，还是带 WAV / RIFF 头？
- **对应缺口**：无缺口编号（平台自实现的偏差点，S14）。
- **平台当前假设**：**发送裸 PCM**——平台侧音频产物（录音 artifact、TTS 落盘结果）通常是 WAV 容器，发送前拆掉 44 字节头，**不做任何重采样**。拆解结果里的采样率 / 声道 / 位深由平台记录，便于与终端声明的采样率比对。实现见 `sdui/v2/audio/WavPcm`。
  **不做重采样是刻意的**：终端在能力 Schema 的 `audio` 中声明自己接受的采样率，静默重采样会把「声音不对」变成只能靠耳朵发现的问题。若两端采样率不一致，平台会如实记录并上报差异，而非掩盖。
- **阻塞**：4.8、5.8.2
- **假设不成立时的动作**：低代价（若终端要 WAV 头，保留而非剥离头即可），但**采样率不一致的处理策略需要终端明确表态**：是终端自己处理，还是要求平台转换。

## 5. 与缺口表的对应

`12_DESIGN_NOTES.md` 的缺口表（G\*）记录「文档没定义、平台自己定了」的地方；本清单记录「**需要终端核对**」的部分。两者是多对多：

- 有缺口无待确认项：平台自实现且不影响终端（如 S 系列），无需确认。
- 有待确认项无缺口：模型未定义功能（T6 / T13 / T14 / T16），需要终端提供输入而非核对假设。
- 其余为一一或一对多映射，已在各项的「对应缺口」字段中标注。

高风险项（G2 / G10 / G13 / G20）与 T2 / T3 / T4 / T7 / T12 对应，是本清单中改动代价最高的一组，**建议最先谈**。
