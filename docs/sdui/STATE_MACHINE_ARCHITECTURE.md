# SDUI 状态机架构设计

## 一、背景与动机

### 1.1 当前工作流模块的问题

当前 SDUI 工作流模块基于通用 DAG（有向无环图）执行引擎，节点类型包括触发器、输入、控制、输出四大类。在实际使用中暴露出以下架构层面问题：

**输出端不统一**：命令和 section 是两种完全不同的输出形态。命令是"命令名 → 参数 schema"的扁平模型，各命令间语义无关。Section 是嵌套的组合结构（page 元数据 + sections 数组 + 各类型相关字段），配置复杂度远高于命令。两者作为统一"节点"暴露时，用户面对的是一个无结构的操作列表，而非编排体验。

**输入端未明确**：所有设备输入事件通过同一个 `EventPayload` 通道流入，靠 `eventId` 字符串区分类型。后端无法在定义/校验时知晓事件的 payload 结构，也无法声明"此流程接受以下类型的输入"。更根本的问题是，事件的业务含义绑定到渲染上下文——同一个 `toggle.change` 在不同 section 上代表完全不同的语义，但当前系统只能按 `sectionId` 做字符串过滤，而 `sectionId` 是运行时标识符，非类型标识符。

**执行引擎局限**：输出节点为 fire-and-forget 模式，不等待终端确认。命令生命周期事件（ACK、超时）只能触发新的工作流运行，无法回连到当前运行。缺少基本的自动化原语——无定时触发、无循环/迭代、无延迟等待、无 HTTP 调用。旧代码中存在的 `LoopNode`、`FetchNode`、`LlmChatNode` 等已全部删除。

**设备绑定与复用冲突**：流程定义中写死 `deviceId`，导致流程绑定到特定设备，无法跨设备复用。Debug 模块与工作流模块双轨并行，各自维护状态和验证逻辑，缺乏统一的类型和契约层。

### 1.2 重新定位

经过分析，SDUI 终端交互的核心不是"通用工作流编排"，而是**"根据输入事件动态改变设备屏幕内容"**。屏幕（Section 集合）就是应用状态。因此架构应从通用 DAG 引擎转向以 Section 为核心的 **UI 状态机**，收窄问题域、降低抽象复杂性。

---

## 二、核心设计原则

1. **平台为唯一类型注册中心**：所有 section 类型、命令 schema、事件类型均在平台预定义，工作流定义引用平台类型 ID，校验在保存时完成。

2. **Section 为状态的核心载体**：一切编排的最终反馈体现为 section 数据的变化（新增、删除、字段更新）。命令（灯光、音频等）作为独立的非视觉副作用，与 section 操作并列。

3. **槽位抽象代替设备绑定**：设计时面向槽位（角色引用），部署时槽位映射到实际设备。实现流程模板可复用。

4. **终端无状态，平台有状态**：终端仅作为展示端和输入源。平台维护权威状态，断线重连后全量恢复。槽位多设备时命令广播到所有设备。

5. **权威状态 + 自动传输优化**：平台始终维护完整的 section 权威状态。每次状态变化后自动计算新旧差异，差异小走 patch（增量），差异大走 scene（全量）。用户无需关心底层传输方式。

---

## 三、整体架构

架构分为四层：

```
┌──────────────────────────────────────────────────────┐
│               L1: 平台类型注册中心                      │
│   统一管理 section 类型、命令 schema、事件类型           │
│   所有 I/O 的类型定义均在此注册                         │
└──────────────────────────────────────────────────────┘
                         ↓
┌──────────────────────────────────────────────────────┐
│            L2: 流程定义（可复用模板）                    │
│   状态图 + 转移规则 + 动作组                            │
│   设计时面向槽位，与物理设备解耦                         │
└──────────────────────────────────────────────────────┘
                         ↓
┌──────────────────────────────────────────────────────┐
│          L3: 部署实例（模板 → 实际设备绑定）             │
│   槽位 → deviceId 映射                                │
│   一个模板可产生多个部署实例（多房间、多场景）            │
└──────────────────────────────────────────────────────┘
                         ↓
┌──────────────────────────────────────────────────────┐
│            L4: 设备投影 + 协议适配                      │
│   section → scene/patch（自动差异计算）                 │
│   command → 命令分发（槽位多设备广播）                   │
│   输入 ← 事件接收（注入 deviceId + 槽位）               │
└──────────────────────────────────────────────────────┘
```

## 四、L1: 平台类型注册中心

### 4.1 职责

平台是所有 I/O 类型的唯一权威来源。所有 section 类型、命令 schema、事件类型在平台预定义，确保：
- 前端编辑器可查询平台获取"设备支持哪些类型"
- 工作流定义引用平台类型 ID，不依赖裸字符串
- 校验在保存时完成，非运行时发现不匹配

### 4.2 管理内容

| 类型类别 | 内容 | 来源 |
|----------|------|------|
| Section 类型 | 12 种 section 的字段定义、约束、交互事件声明 | 平台定义（现有 SectionTypeCatalog） |
| 命令 Schema | 每种命令的参数定义、类型、约束、默认值 | 设备能力上报 + 平台增补 |
| 事件类型 | 每种事件的 payload 结构、产生来源 | 平台定义 + section 交互事件声明 |

### 4.3 Section 类型的交互事件声明

每种 section 类型在注册时声明其可产生的交互事件：

- `action_section` → 产生 `action.click` 事件（payload: sectionId, buttonId, pageId）
- `toggle_section` → 产生 `toggle.change` 事件（payload: sectionId, optionId, active）
- `list_section` → 产生 `list.select` 事件（payload: sectionId, itemId, rowData）
- `overlay_section` → 产生 `overlay.confirm` 事件（payload: sectionId）

这使得输入事件的注册可以随 section 变化而动态更新。

## 五、L2: 流程定义（UI 状态机）

### 5.1 状态

**状态 = 单个 page 的完整 section 集合（权威状态）。**

- 每个流程定义包含一个 page
- page 定义其绑定的槽位集合（设计时引用，非真实设备）
- 每个状态描述"在这个状态下，page 上应该有哪些 section，每个 section 的完整字段"
- 状态是声明式的——描述"是什么"，而非"怎么变"

### 5.2 转移

**转移 = 输入事件 → 动作组。**

```
转移 "收到新邮件"
  触发：事件输入（来自某个槽位的 button.press）
  动作组：
    section 操作：
      ├─ 新增 overlay_section → 目标槽位：显示器（主屏）
      └─ 更新 metric_section 字段 → 目标槽位：显示器（主屏）
    command 操作：
      └─ rgb.set(color=blue, blink=true) → 目标槽位：指示灯
```

**Section 操作**（影响 UI 状态）：

| 操作类型 | 说明 |
|----------|------|
| 新增 section | 向 page 添加一个指定类型的 section |
| 删除 section | 从 page 移除指定 section |
| 更新 section 字段 | 修改已有 section 的部分字段值 |

**Command 操作**（非视觉副作用，不影响 UI 状态）：

| 操作类型 | 说明 |
|----------|------|
| 执行命令 | 向目标槽位的设备发送命令（灯光、音频等） |
| 平台能力调用 | 执行 TTS、STT 等平台侧能力 |

**关键设计：page 操作与 command 操作分离。** page 只管屏幕上的 section 变化，灯光、音频、马达振动等是独立的命令动作，各自绑定各自的目标槽位。状态只反映 section 集合（UI 快照），命令是瞬时的（发完即结束，不构成持续状态的一部分）。

### 5.3 输入事件的动态注册

输入事件列表不是静态的，而是随流程定义的 section 变化而动态更新：

- **静态输入**：设备物理能力（按钮、传感器等），初始化时注册
- **动态输入**：section 携带的交互事件，随 section 新增/删除而变化
- 删除一个 section 后，其关联的输入自动从可用列表移除
- 输入按槽位分组展示，用户能清晰知道"这个触发来自哪个槽位"

**动态列表的特殊处理**：对于动态渲染的列表（如 todo list），编辑时刻无法预知每个 item 的具体内容。输入注册的粒度是**模板/来源级**而非实例级：
- 不注册"list-item-0 的选中"、"list-item-1 的选中"
- 而是注册"todo-list-section 的选中事件"
- 事件携带行数据（rowData），转移从数据上下文中获取具体信息

### 5.4 槽位引用体系

流程定义中不使用真实 deviceId，而使用槽位引用：

| 引用类型 | 解析时机 | 用途 |
|----------|----------|------|
| `slot:显示器` | 部署时映射 | 明确角色的设备，如"主显示屏" |
| `slot:指示灯` | 部署时映射 | 灯光设备 |
| `$trigger_slot` | 运行时解析 | 触发事件的设备所在槽位，用于"在哪触发就在哪反馈" |
| `$trigger_device` | 运行时解析 | 触发事件的具体设备 ID |

槽位是流程设计时的抽象占位符。输入事件按槽位分组展示，输出动作的目标是槽位。流程模板完全不感知物理设备。

### 5.5 数据上下文

数据在转移链中通过上下文传递。上下文包含以下命名空间：

| 命名空间 | 内容 | 生命周期 |
|----------|------|----------|
| `$event` | 触发本次转移的事件 payload | 单次转移 |
| `$context` | 转移间传递的业务数据 | 从写入到被覆盖或状态切换 |
| `$http` | 最近一次 HTTP 调用的返回值 | 单次转移 |
| `$slot` | 当前槽位映射信息 | 部署实例级 |

**数据绑定方式**：section 的字段值可以引用上下文中的变量：

```
hero_section.title = "$context.todo_title"
list_section.items = "$http.response.data"
```

模板变量解析在动作执行前完成，动态列表的批量实例化也在此阶段处理——对数组数据的每一项生成对应的 section 实例。

### 5.6 动态列表处理

采用**模板 + 批量实例化**方式，而非完全参数化状态：

**设计时定义：**
```
模板 "todo-list-item"
  类型：list_section
  动态绑定：items = "$http.response.data"
  行模板：{ title: "$row.title", subtitle: "$row.due" }
  输入事件：list.select（携带 rowData）
```

**运行时：**
1. HTTP 调用返回数组数据
2. 平台对数组每项按行模板生成 section 实例
3. 打包为 patch 或 scene 下发
4. 用户选中某项时，事件携带 rowData 写入 `$context.selected_item`
5. 后续转移从 `$context.selected_item` 读取数据渲染详情

这样"详情"状态本身不需要参数化——它引用的数据来自上下文，而不是状态定义时的参数。

### 5.7 状态的转移类型

每次转移后，平台比较新旧状态（完整的 section 集合），计算差异：

- **差异小**（如更新一个字段、弹一个 overlay）：自动构造 patch 下发
- **差异大**（如超过 50% 的 section 变化）：自动降级为 scene 全量推送
- **设备重连**：直接全量 scene 推送，恢复到断开前状态

用户只需定义"目标状态是什么样的"，无需关心底层用什么方式传输。

### 5.8 Overlay 处理

Overlay（弹窗/浮层）采用**无状态栈模型**处理：

- 弹出 overlay = 向当前 page 新增一个 overlay_section
- 关闭 overlay = 从当前 page 删除该 overlay_section
- 所有转移都是"触发 → 动作组"，不区分"前进"和"返回"
- 编辑器中"关闭 overlay"的转移由用户显式定义

优势：与 patch 机制完全兼容，编辑器逻辑统一。关闭 overlay 时可附带更新底层 section（如刷新数据），灵活性高于自动状态栈。

## 六、L3: 部署实例

### 6.1 槽位映射

部署时将流程模板中的槽位映射到实际设备。一个模板可产生多个部署实例：

```
部署 "会议室看板"
  槽位 显示器 → device-A（会议大屏）
  槽位 指示灯 → device-B（灯带）
  槽位 副屏   → （未绑定，此部署不使用）

部署 "前台看板"  
  槽位 显示器 → device-C（前台大屏）
  槽位 指示灯 → device-D（灯带）
```

### 6.2 部署实例生命周期

- 每个部署实例独立维护当前状态（所在状态节点 + section 权威状态 + 数据上下文）
- 一个模板的多个部署实例互不干扰
- 设备断线重连后，从部署实例的权威状态全量恢复到设备
- 设备更换时，更新部署实例的槽位映射即可

### 6.3 同槽位多设备

当一个槽位绑定多个设备时（如"指示灯"绑定了两个灯带），命令采用**广播模式**——向该槽位下所有设备发送。Section 推送同样广播到该槽位下所有显示设备。

## 七、L4: 设备投影与协议适配

### 7.1 Section 推送

- 平台维护权威 section 状态
- 每次状态变化后计算新旧差异
- 差异小时构造 patch 下发（现有 MSG_TYPE_SECTION_PATCH = 17）
- 差异大时构造 scene 下发（现有 MSG_TYPE_SECTION_SCENE = 16）
- 按目标设备能力做适配（COMPACT vs RICH 模式、数据截断等，复用现有 SectionCapabilityAdapter）

### 7.2 命令分发

- 槽位解析为 deviceId 列表
- 多设备时广播到所有设备
- 通过现有 CommandService + SduiProtocolService 下发
- 命令生命周期事件（ACK、超时等）进入事件总线，可供流程转移使用

### 7.3 事件接收

- 设备输入事件（二进制 EVENT_INPUT 帧）通过现有 EventInputHandler 接收
- 注入 deviceId 和槽位信息
- 路由到当前部署实例的状态机，匹配转移规则
- 未匹配的事件丢弃（或记录日志）

### 7.4 设备重连恢复

- 设备断线重连时，查找该设备所属的部署实例
- 获取部署实例的当前权威状态
- 全量 scene push 恢复设备显示
- 不需要流程重新触发——这是设备恢复，不是业务重置

## 八、架构优势总结

| 维度 | 当前 DAG 工作流 | 新架构 |
|------|----------------|--------|
| 编排模型 | 通用节点图，抽象且复杂 | Section 状态机，直观可视化 |
| 用户心智 | 节点连线图 | 页面状态 + 转移规则 |
| 状态管理 | 隐式 context map | 显式 section 权威状态 |
| 输入处理 | 裸 eventId 字符串匹配 | 动态输入列表 + 数据上下文 |
| 输出组织 | 命令/Section/平台能力混杂 | page 操作 与 command 操作分离 |
| 设备绑定 | 写死 deviceId | 槽位抽象 + 部署时映射 |
| 复用性 | 绑定设备，无法跨设备 | 模板化，多部署实例 |
| 传输策略 | 手动选择 scene/patch | 自动差异计算 + 智能选择 |
| 终端角色 | 有状态假设 | 明确为无状态展示端 |
| Debug 与编排 | 双轨并行 | 统一平台管理 |

## 九、实现策略建议

### 9.1 实现顺序

**第一阶段：核心数据模型 + 状态机引擎**
- 定义状态、转移、动作组、槽位、部署实例的数据模型
- 实现状态机执行引擎（事件匹配 → 转移选择 → 动作执行 → 状态更新）
- 实现权威状态管理（section 集合的增删改 + 差异计算）

**第二阶段：槽位系统 + 部署管理**
- 实现槽位抽象和映射机制
- 实现部署实例的创建、绑定、生命周期管理
- 实现设备重连恢复

**第三阶段：动态输入注册 + 数据上下文**
- 实现输入事件的动态注册（随 section 变化）
- 实现数据上下文传递和模板变量解析
- 实现动态列表的模板批量实例化

**第四阶段：编辑器集成 + 前端适配**
- 设计可视化状态编辑器
- 按槽位分组展示输入
- 提供 section 模板编辑器

### 9.2 可复用的现有模块

| 现有模块 | 复用方式 |
|----------|----------|
| SectionTypeCatalog | 直接纳入 L1 类型注册中心 |
| SectionScene / SectionPatch | L4 传输层的数据载体 |
| SectionOrchestrationService | L4 的 section 推送 + 状态记忆 |
| SectionCapabilityAdapter | L4 的设备能力适配 |
| SectionDataCodec | section 数据编解码 |
| CommandService | L4 的命令分发 |
| EventInputHandler | L4 的事件接收，增加槽位注入 |
| DeviceSessionManager | L4 的设备会话管理 |
| CapabilityCatalog | 纳入 L1 类型注册中心 |

### 9.3 不需要保留的模块

旧工作流模块的 DAG 引擎、节点模型、通用触发器体系不再适用。新架构已作为独立状态机模块实现，不再与旧工作流包混合；旧运行代码已移除。

## 十、待进一步明确的设计细节

以下问题在实现阶段需要进一步细化：

1. **状态编辑器的交互范式**：用户如何创建状态、定义转移？是状态图连线还是表单式定义？
2. **HTTP 调用的定义方式**：是作为转移中的一个动作步骤，还是作为独立的能力节点？如何定义请求模板和返回值到上下文的映射？
3. **转移的优先级和冲突解决**：如果同一个事件匹配了多个转移规则，如何选择？
4. **Section 模板编辑器的交互**：用户如何定义"动态列表的每项模板"？如何在编辑器中预览？
5. **部署实例的持久化**：权威状态是仅内存还是需要持久化到数据库？如果需要持久化，策略是什么？
