# 核心交互模型

## 1. 模型目标

旧方式把一次用户交互拆成多轮端云命令，由平台在执行过程中逐步遥控设备，无法可靠满足长链路、跨云端和实时硬件反馈并存的场景。

新模型将可预先确定的即时响应交给终端执行，同时保留平台处理复杂业务的能力：

```text
终端事件
├── 本地立即响应
└── 与云端进行必要交互

云端耗时处理完成
└── 以新的输入驱动终端后续展示或动作
```

## 2. 有限有序响应序列

一个 Trigger 可以绑定一个或多个 Response。多个 Response 按声明顺序提交，构成有限、有序、不可编程的本地响应序列。

```text
Trigger
→ Response 1
→ Response 2
→ Response 3
```

响应序列可以复用终端已经声明的设备动作和平台交互动作，但不支持：

- 条件表达式、分支和循环；
- 动态跳转和任意延时节点；
- 等待云端业务结果；
- 动态调用外部接口；
- 将动作结果重新注入绑定表。

长时间动作不会使响应序列一直处于执行状态。动作完成其同步启动或提交边界后，响应序列即可继续；具体边界由对应能力定义。

该模型用于组合本地即时响应，不承担平台业务编排，也不是终端工作流引擎。

### 2.1 失败语义

每个 Response 在终端内部返回成功或错误：

- 成功时继续提交下一个 Response；
- 错误时立即停止，不再执行后续 Response；
- 已经成功的 Response 不做通用回滚；
- 动作被接受后发生的异步错误，不重新恢复原响应序列。

本地 Response 的执行结果默认只在终端内部使用，不自动产生网络消息。平台主动下发的请求在整条响应序列结束后只返回一次汇总结果，而不是逐步上报每个 Response。

不同能力需要分别定义同步成功边界。长时间动作的成功表示已经完成必要校验并进入对应运行阶段，不表示整个动作生命周期已经结束。

## 3. Trigger 来源

Trigger 必须来自终端明确声明并允许配置的输入源。首期支持物理按钮和一种云端 Trigger：

```text
button.*
platform.trigger.*
```

物理 Trigger 由输入模块产生。云端 Trigger 由平台通过 Socket 请求触发，并携带平台预先配置的不透明 `token`。终端使用 token 在当前业务配置中查找对应绑定，执行已经配置的 Response 序列。

```text
平台配置：platform Trigger(token) → 预设 Response 序列
平台请求：business.trigger(token)
终端执行：查找 token → 执行预设 Response 序列 → 返回最终结果
```

token 本身就是云端 Trigger 的控制参数，不再增加额外开关、业务类型或动态动作参数。终端不解释 token 的业务含义，也不接受请求临时携带新的 Response 列表。找不到 token、当前无活动业务或执行资源不足时返回错误。

平台请求只接收整条响应序列的一次最终成功或错误结果，不逐步上报每个 Response。

能力动作的完成、失败和内部状态变化不自动成为 Trigger，避免形成递归执行路径。首期不增加其他 Trigger 来源。

## 4. 平台交互

首期提供一个专用 Response：

```text
platform.interaction.report
```

平台在下发绑定时为该 Response 提供一个有长度上限的不透明 `token`。终端只负责保存并在触发时原样上报，不解析、不修改，也不把它解释为 URL、命令、本地动作或业务参数。

```text
平台配置：Trigger → platform.interaction.report(token)
终端触发：device_id + token → 平台
```

`token` 标识平台预先配置的交互含义，同一绑定多次触发可以返回相同 token。平台根据设备和 token 恢复业务上下文、维护业务状态并决定后续操作。是否需要额外的触发序号，在设计重试、去重或离线补发时再决定。

该动作通过有界异步发送通道提交，不等待网络发送完成或平台业务结果。成功只表示消息已被终端发送流程接管；离线且不允许暂存、队列已满、token 非法或无法提交时返回错误，并按响应链规则截止后续 Response。

首期不支持任意 JSON 参数、离线无限缓存或自动重试。普通本地 Response 也不会因为成功执行而自动产生平台上报。

平台后续返回的 UI 或设备操作是新的独立命令，不是原响应序列的继续。

终端上报与云端 Trigger 采用对称的最小模型：

```text
终端 → 平台：platform.interaction.report(token)
平台 → 终端：business.trigger(token)
```

两种 token 都由平台创建和维护，终端只负责保存、匹配或原样传递。二者可以采用相同的字段形式，但分别属于当前配置中的上报 Response 和云端 Trigger，不隐含递归关系。

## 5. 持续能力与音频

音频等持续能力自行维护必要的内部运行状态，不为此引入通用 Fact 层或全局状态机。

录音与播放互斥，同一时间只允许一种主要音频行为。正在录音时请求播放、正在播放时请求录音，默认返回 `audio_busy`，不自动抢占。明确的停止动作、`business.reset`、音频错误、等待超时和系统重启可以终止当前音频行为。短暂网络断开本身不终止音频。

录音优先使用含义明确的动作：

```text
button.down  → audio.record.start
button.up    → audio.record.stop
```

明确需要单击切换时，可以提供：

```text
button.short_press → audio.record.toggle
```

`toggle` 只是音频模块根据真实状态解释的便利动作，不承担状态同步职责，也不替代 `start/stop`。

UI 不随录音状态自动更新。录音使用开始和结束提示音、录音期间 RGB 灯效等固定非 UI 反馈。正常停止、超时和异常退出都必须结束相关反馈。

音频流开始、数据传输、正常结束和异常终止由音频协议自身表达，不抽象为全系统 Fact，也不重新进入本地绑定表。

开始和结束提示音不与录音重叠：开始提示音结束后再进入录音，停止并释放录音资源后再播放结束提示音。首期不设计混音。

录音上传缓冲区满时立即异常终止，不丢弃中间片段后继续录音，也不等待缓冲区后续恢复。终端必须停止采集、丢弃尚未发送的缓冲数据、结束录音反馈并释放录音运行状态。若连接仍可用，可以尽力上报 `buffer_full` 异常，但上报失败不能阻塞本地清理；平台通过连接状态和超时兜底未收到的结束通知。

网络暂时不可用时，录音继续采集到有界缓冲；新连接接管后继续发送缓冲和后续数据。该机制只用于吸收短时波动，不保证跨连接精确无损交付，也不增加分片确认和重传。播放在暂时没有新数据时保持等待，新数据恢复后继续；超过播放等待时限才结束并清理。

## 6. 业务清理与配置更新

业务运行状态清理和声明式配置更新是两个不同操作，不因全量更新配置而自动清理全部业务状态。

### 6.1 业务清理

平台通过独立的 `business.reset` 语义要求终端清理当前业务环境。该操作至少包括：

- 停止录音、音频上传和播放；
- 结束业务提示音和 RGB 灯效；
- 清除当前业务 UI 和本地导航状态；
- 取消未完成的响应序列和业务定时任务；
- 清除旧业务尚未发送的交互上报；
- 清除当前绑定和未完成的按钮手势；
- 进入无活动业务的安全状态。

网络连接、设备身份、配网、电源、系统诊断和缓存资源等系统基础状态不属于业务清理范围。

所有可能持续运行或占用资源的能力都必须提供有界、可重复调用的停止或清理机制。清理不能无限等待；正常停止失败后需要进入模块强制恢复，仍无法恢复时由终端报告错误并进入安全状态，必要时重启。

### 6.2 全量配置更新

平台通过 `business.update` 语义下发完整目标配置。终端先完整解析和校验，再原子替换当前配置。

首期不提供绑定级 `add`、`modify`、`delete` 等增量命令。即使只修改一个绑定，平台也发送完整最新配置，避免增量顺序、部分应用、版本漂移、断线漏包和事务回滚问题。

全量 `update` 不等于 `reset`，不会自动停止已经运行的录音或播放。为了避免一次按压跨越新旧绑定，更新时需要：

1. 校验并暂存新配置；
2. 暂停分发新的 Trigger；
3. 等待当前短响应序列到达同步结束边界；
4. 原子替换配置；
5. 清除未完成的按钮手势；
6. 等当前按键释放后恢复 Trigger 分发。

### 6.3 业务切换

整体业务切换由平台控制，首期采用：

```text
business.reset
→ business.update(完整新配置)
```

如果 reset 成功后在 update 前断线或更新失败，终端保持无活动业务状态，不恢复已经清理的旧业务。平台重连后重新下发完整配置即可恢复。

首期不增加把清理和更新封装为事务的组合命令；确有无空窗切换需求时，再评估原子 `business.replace`。

## 7. 当前待讨论

- 不同能力的同步启动或提交成功边界；
- 持续动作在按键释放丢失时的终止规则；
- 音频缓冲区的准确大小和最大录音时长（实现阶段结合资源测试确定）。
