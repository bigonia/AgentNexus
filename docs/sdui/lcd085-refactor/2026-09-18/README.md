# LCD_085 系统重构设计

> 建立日期：2026-09-18  
> 文档性质：重构前的系统设计规范，随讨论持续更新  
> 当前阶段：需求与架构决策

## 1. 重构背景

当前系统定位为软件定义的物理交互终端：平台定义业务并进行编排，终端负责业务展示、硬件交互和部分流程执行。
现有实现已经具备显示、按键、音频、RGB、网络连接等基础能力，但这些能力的组织方式无法稳定支撑实际业务。

目前存在两个主要矛盾。

### 1.1 云端微观遥控造成长链路问题

现有交互偏向由平台逐步下发细粒度命令。一次按键操作可能经历：

```text
按键上报
→ 平台判断业务状态
→ 下发 RGB 或屏幕反馈
→ 下发录音等硬件命令
→ 终端再次上报状态
→ 平台继续后续处理
```

当流程涉及云端服务、LLM、第三方 API 或跨设备协作时，多次网络往返会带来：

- 用户操作后不能立即获得反馈；
- 网络延迟、丢包或重试使终端状态与平台状态脱节；
- 平台需要理解并维护大量设备微观执行状态；
- 长流程中的超时、取消、部分失败和恢复难以处理；
- 本可在终端立即完成的硬件联动被网络质量限制。

此前的工作流模式不能有效解决这类长链路和跨云端耗时问题，因此本轮重构需要建立新的事件对交互模式：平台预先定义终端可执行的事件与响应关系，终端完成及时、有限的本地流程，平台异步处理复杂业务。

事件对不是把完整工作流引擎搬到终端。它能表达多大范围的本地流程、如何处理失败以及如何与云端后续结果衔接，是本轮首先需要确认的设计问题。

### 1.2 面向全部终端的通用 UI 抽象不可行

此前的 UI 以 Section 为核心，希望通过一套抽象同时满足不同终端、屏幕类型和业务场景。实际使用表明，这个目标不可行：不同设备在屏幕尺寸、显示能力、输入方式和交互模型上存在本质差异，统一模型要么无法充分表达具体产品，要么只能持续增加类型、属性和例外。

当通用 UI 同时覆盖触摸屏与非触摸屏时，问题更加明显。焦点、点击、手势、页面层级、导航和控件状态需要采用不同的交互语义；将它们放入同一套 Section 抽象，会使终端渲染、平台配置、协议和状态管理的复杂度迅速膨胀。

因此，本轮 UI 重构不是精简若干 Section，也不是继续改良一套跨设备 UI 协议，而是收缩产品边界：

- 只面向固定终端类型 LCD_085；
- 设备为小屏、无触摸，主要通过有限物理按键交互；
- UI 由 LCD_085 独立维护和开发；
- 不兼容其他屏幕、触摸设备或产品形态；
- 围绕该设备持续打磨完整、可用且一致的产品体验。

LCD_085 最终采用什么页面和渲染模型仍需结合产品场景讨论，但“单一设备、独立产品化”已经是 UI 重构的确定边界。

### 1.3 设计结论与实现细节混杂

此前讨论中，系统方向、候选方案、协议字段和代码实现细节容易同时出现，导致尚未确认的想法看起来像既定规范，也缺少清晰的决策顺序。

本轮先确定系统功能、端云边界和模块职责，再设计协议与代码结构。

## 2. 主要重构方向

### 2.1 从云端工作流遥控转向事件对协作

- 平台继续负责业务定义、长期状态和复杂编排；
- 终端执行预先允许、边界明确的本地响应；
- 即时硬件反馈不等待云端；
- 终端事件可异步通知平台；
- 云端耗时处理完成后，以新的输入驱动终端后续展示或动作；
- 不在终端引入开放式脚本、任意条件、循环和跨云端等待。

### 2.2 围绕 LCD_085 重建 UI 功能模型

- 放弃用一套 Section 抽象覆盖全部终端和屏幕类型；
- 将 LCD_085 作为独立产品维护，不承担其他设备的兼容需求；
- 以 128×128 小屏、无触摸和有限物理按键为固定设计条件；
- 根据真实业务场景确定屏幕内容、导航和状态反馈；
- 在固定产品边界内打磨完整、一致的 UI 与交互体验。

### 2.3 重新划分系统和模块边界

- 明确平台业务状态与终端运行状态的区别；
- 明确输入、事件执行、音频、显示、反馈、连接和资源等职责；
- 对断网、上下文切换、部分失败和重启给出可解释行为；
- 在这些结论稳定后，根据需要重新设计端云协议和代码架构。

## 3. 已确认的设计基础

- 平台负责业务定义、长期业务状态、复杂编排和外部系统交互。
- 终端负责业务展示、物理输入、及时本地响应、边界受限的流程执行和必要的云端交互。
- LCD_085 是唯一设计和验收目标；UI 只服务 128×128、无触摸、使用有限物理按键的固定产品。
- 不为其他屏幕、触摸设备、旧 Section、旧协议或现有代码结构保留兼容设计。
- 本地即时响应不等待云端业务完成，终端也不承载开放式工作流。
- 协议和代码结构在系统行为与模块边界确定后设计，必要时可以整体重构。

## 4. 当前讨论进度

事件对的基本结构已经确认，详见[交互模型](01_INTERACTION_MODEL.md)：一个 Trigger 可以绑定有限、有序、不可编程的 Response 序列；执行失败时截止后续响应，已经完成的响应不做通用回滚。终端上报和云端 Trigger 都使用平台维护的不透明 token，终端不解释业务含义。业务状态清理与配置更新采用独立命令，配置只做全量原子替换，不支持增量 patch。

网络波动和 WebSocket 重连不会清理当前业务上下文。录音依靠有界本地缓冲继续，播放在缺少新数据时等待到超时；只有平台明确 reset、资源耗尽或模块自身超时/错误才结束相应状态。

系统界面只用于业务接入前的启动、配网、设备注册和等待阶段。进入业务后平台独占屏幕，终端系统状态不得覆盖或插入平台主视图；只有业务尚未建立、被 reset 清空，或平台/网络被确认断开时，系统界面才能接管显示。

2. Binary 大数据协议及代码架构。

## 6. 维护原则

- 已确认内容直接写入所属主题，不另建重复的决策台账。
- 尚未确认的关键问题放在所属文档末尾，不单独维护 backlog。**例外**：与终端对接的待确认项（T1–T16）单独维护于 [终端对接待确认清单](../../../terminal/TERMINAL_CONFIRMATIONS.md)——它横跨交互模型、协议模型与三份实施文档，且需要与终端逐条回填确认结果，散落登记会让"哪些已确认、哪些还卡着"无法收敛。这是对外协作清单，不是设计 backlog。
- 新结论取代旧结论时直接修改正文；只有确有追溯价值时才保留变更说明。
- 消息字段、API、任务、文件和数据结构等实现细节，在系统边界稳定后再讨论。
