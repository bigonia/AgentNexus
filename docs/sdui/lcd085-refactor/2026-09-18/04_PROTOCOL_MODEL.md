# 端云协议模型

## 1. 目标

协议只服务 LCD_085 固定产品，允许不兼容现有协议。目标是统一命令、结果、业务配置和二进制数据的表达，同时避免为不可恢复的数据建立复杂续传机制。

协议采用单一 WebSocket 连接：

```text
JSON 控制消息
├── 请求与最终结果
├── 业务 reset、update 和 trigger
├── 终端平台交互上报
└── 音频、图片、Canvas 等生命周期控制

Binary 数据
├── 音频数据
├── 图片数据
├── Canvas 帧
└── 能力 Schema 与其他较大对象
```

控制语义统一使用 JSON；二进制只承载不适合放入 JSON 的数据，不再保留 UI3 TLV 输入、Binary ACK/ERROR、Base64 音频等重复路径。

## 2. 设备身份与连接接管

建立 WebSocket 时已经通过连接参数携带唯一 `device_id`。连接建立后的消息不重复携带设备标识，平台根据 Socket 归属识别设备。

同一 `device_id` 同一时刻只有一个有效连接：

```text
新连接建立
→ 平台将新连接设为当前连接
→ 旧连接失效
→ 旧连接后续消息全部忽略
```

WebSocket 连接生命周期不等于业务生命周期。网络波动导致的新连接不会自动清除平台保存的业务状态，也不会触发终端 `business.reset`。

## 3. 轻量连接识别

连接建立时除 `device_id` 外，只需要提供：

- `protocol_version`；
- `capability_hash`。

首期不使用 `boot_id`。平台无需区分网络重连和终端重启；每次新连接接管完成后，都重新发送该设备当前的完整 `business.update`：

```text
网络重连
→ 相同配置幂等替换

终端重启
→ 重新获得当前完整配置
```

由于 `business.update` 不等于 `business.reset`，普通网络重连时重新下发配置不会主动停止终端仍在运行的持续动作。

## 4. 能力 Schema 与 hash

终端不再只上报能力名称，而是提供机器可校验的完整能力 Schema。Schema 至少描述：

- 协议和 Schema 版本；
- 支持的 Trigger；
- 支持的 Action 及其参数类型、必填项、范围和枚举；
- Action 可用于本地绑定、平台命令或两者；
- Section、图片和 Canvas 等 UI 能力及资源限制；
- 音频和其他二进制数据格式及限制。

Schema 使用受限的机器描述格式，不要求终端支持完整通用 JSON Schema。动作的自然语言解释和业务速查表由平台维护，不随每次连接发送。

Schema 的准确语法、字段组织和是否采用标准 JSON Schema 子集留到实现阶段结合平台校验方式确定。设计目标是完整表达必要参数约束，同时避免重复字段、自然语言和与执行无关的元数据。

完整 Schema 在构建时生成稳定的 `capability_hash`。平台按 hash 缓存 Schema：

```text
hash 已知
→ 直接使用缓存能力

hash 首次出现或发生变化
→ 平台请求完整 Schema
→ 终端发送 Schema
→ 平台校验内容与 hash
→ 保存并启用
```

同一固件能力的多个终端可以共享平台侧同一份 Schema。终端不需要知道平台缓存状态，平台决定是否请求完整内容。

只有首次注册、未知 hash 或 Schema 校验失败时，终端进入能力同步阶段并暂不接受平台业务。普通已知 hash 的连接接管不重复执行完整初始化。

## 5. 请求、结果和事件

JSON 控制面只使用三种最小结构，不增加通用 `type`、`topic`、`action`、时间戳或 metadata 字段。

平台请求：

```json
{
  "id": "req-1",
  "name": "business.reset",
  "body": {}
}
```

终端成功结果：

```json
{
  "id": "req-1",
  "ok": true
}
```

终端错误结果：

```json
{
  "id": "req-1",
  "ok": false,
  "error": "audio_busy"
}
```

终端主动事件：

```json
{
  "name": "platform.interaction",
  "body": {
    "token": "opaque-token"
  }
}
```

判定规则为：

```text
平台 → 终端，id + name  = request
终端 → 平台，id + ok    = result
终端 → 平台，name 无 id = event
```

空 `body` 可以省略。`name` 只出现在请求和主动事件中，`ok` 只出现在结果中，主动事件不携带请求 `id`。

平台主动发起且需要确认的请求必须携带唯一 `id`。终端对整个请求只返回一次最终成功或错误，不逐步上报内部 Response。

本地事件对中的 Response 只产生终端内部成功或错误。只有显式配置 `platform.interaction.report(token)` 时，终端才向平台发送业务交互。

已确认的核心业务消息语义为：

```text
business.reset
business.update
business.trigger(token)
platform.interaction.report(token)
```

准确消息信封、字段名称和最小错误集合在协议细化时确定。

音量、亮度、重启和配网等现有功能使用独立的系统命令名称，例如：

```text
system.volume.set
system.brightness.set
system.reboot
system.provisioning.start
```

系统命令不进入业务绑定，不被 `business.reset` 清除。现有音量、亮度、重启和配网的硬件行为可以复用，但对外协议必须完全迁移到统一 request/result：旧 `cmd/control` Topic、旧 action 字段、旧 `cmd/control_ack` 及其他兼容入口全部删除，不允许同一功能保留多种调用方式。音量和亮度等期望值由平台维护，终端不新增持久化和状态恢复协议。

## 6. 断线原则

网络断开和 WebSocket 重连不等于业务 reset。终端保留当前业务配置和能够安全继续的本地状态，平台保留该设备的唯一业务状态，并由新连接接管旧连接。

短暂网络抖动不改变当前显示。只有连接管理确认平台/网络已经断开后，终端才显示系统离线界面；该界面不清除业务主视图，连接恢复后退出并恢复平台显示。

- 断线中的普通请求由平台判定超时，不自动重放；
- 录音继续写入有界本地缓冲，新连接可用后继续发送；
- 录音缓冲区满时立即停止并清理，不等待无限重连；
- 播放缺少新数据时等待，超过播放等待时限后结束并清理；
- Canvas 不补发历史帧，连接恢复后只处理后续新帧；
- 未完成的图片、能力 Schema 或其他有界对象传输可以丢弃并从头重新发送；
- 重连后平台重新下发当前完整业务配置，但不自动执行 `business.reset`。

这是一种有界的弱网容忍，不提供精确跨连接交付保证。终端不能为了等待重连而无限保存音频、对象或业务消息。

## 7. 音频传输边界

同一设备同一方向同一时刻最多存在一个活动音频流。首期音频采用：

```text
JSON audio.start
→ Binary audio data
→ JSON audio.stop / audio.abort
```

首期不使用 `boot_id`、`stream_id`、分片序号、确认位置、重传或断点续传。单连接内 WebSocket/TCP 保证数据顺序；跨连接只依赖设备唯一活动音频状态和有界缓冲继续传输，不保证连接切换边界上的精确去重或补缺。

平台收到开始后维护该设备唯一的音频接收状态。新连接在平台超时前接管时可以继续接收数据；持续超过平台超时时间、终端报告异常或缓冲区满时，平台将当前音频标记为异常终止，并决定丢弃还是使用已经收到的部分音频。终端不替平台决定部分数据的业务价值。

录音缓冲区满时，终端立即停止采集并清空未发送缓冲，不进行恢复、补发或持续重试。连接仍可用时可以发送一次尽力而为的异常结束消息，原因标记为 `buffer_full`；无论该消息是否发送成功，本地音频状态都必须完成清理。平台未收到结束消息时通过超时将当前音频标记为异常终止。

## 8. 有界对象和连续数据

能力 Schema、全屏图片等已知总大小的数据属于有界对象；音频和 Canvas 属于连续数据。两类数据可以复用底层二进制帧封装，但生命周期保持独立。

一期总体原则为：

- 同类数据不并发创建多个活动传输；
- 依赖当前 WebSocket 的有序传输；
- 缓冲、队列和对象大小必须有明确上限；
- 有界对象断线后可丢弃未完成数据，需要时从头重新发送；
- Canvas 消费不过来时丢弃旧帧，优先保留最新帧；
- 二进制数据不能使控制消息和必要系统消息长期饥饿。

以下细节留到大数据协议专项讨论：

- 二进制帧头；
- 对象开始、分片和结束消息；
- 单消息与单对象最大尺寸；
- 是否需要对象 hash、总长度和编码字段；
- Schema、图片、Canvas、音频和资源是否完全共用帧头；
- 各类数据的队列、流控和内存预算。

### 8.1 JSON 与 Binary 混合规则

WebSocket Text Frame 承载 JSON 控制消息，Binary Frame 承载数据本体。两者不重复表达同一数据：

```text
JSON   → 操作名称、参数、生命周期、成功和错误
Binary → 音频样本、像素矩阵、能力 Schema 和资源字节
```

Binary Frame 必须包含最小数据类型标识，使接收端能够区分音频、图片、Canvas 和能力 Schema。首期通过限制同类数据并发，避免引入复杂的 `stream_id` 或 `transfer_id`。

JSON 控制对应数据生命周期，例如：

```text
audio.start → Binary audio data → audio.stop
display.canvas.open → Binary canvas frames → display.canvas.close
display.image.begin → Binary image data → display.image.end
```

同一连接内依赖 WebSocket/TCP 保证 Text 与 Binary 消息顺序。没有活动生命周期时收到对应 Binary 数据应拒绝或丢弃。

为避免大块数据阻塞控制消息：

- 单个 Binary chunk 必须有大小上限；
- 大对象拆为有界 chunk；
- 控制消息优先于 Canvas 和遥测；
- 所有发送与接收队列有固定上限；
- 音频使用稳定的小分片；
- 断线后清除未完成的非续接对象状态；音频按有界缓冲规则等待重连，Canvas 不补历史帧。

## 9. 平台兜底职责

部分可靠性由平台负责，终端不为此维护复杂恢复状态：

- 通过 `device_id` 保证同一终端只有一个当前连接；
- 新连接接管旧连接并屏蔽旧连接的迟到数据；
- 保存设备当前业务配置，新连接可用后重新完整下发；
- 根据 `capability_hash` 缓存、请求和校验能力 Schema；
- 对未收到结果的普通请求执行超时处理；
- 在短时断线期间保留设备唯一音频接收状态，并在等待超时或终端报告异常后标记异常结束；
- 决定是否使用已收到的部分音频；
- 必要时重新发起图片、Canvas 或其他数据操作；
- 控制发送速率，避免超过终端声明的队列和资源上限。

终端负责提供明确的成功、错误、有界等待、异常清理和资源上限，不伪装已经丢失的数据可以精确恢复。

## 10. 后续需要讨论

- 错误名称的最小集合；
- `capability_hash` 的生成和编码方式（实现阶段确定）；
- 平台请求完整 Schema 的控制流程；
- 二进制帧和大对象传输格式；
- 音频、图片和 Canvas 的准确开始、结束和异常消息；
- 连接接管时当前终端持续动作的最终处理规则；
- Ping/Pong、连接超时和重连退避参数。
