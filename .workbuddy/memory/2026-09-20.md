## 0.14.2 T17 结项：切两条边，解耦 ui/v2 与旧能力·事件模型

上一条遗留的 T17（"`ui` 包如何从旧能力 / 事件模型解耦"）经逐类依赖扫描后确认**边界画错了**：不需要动 `ui` 包，旧簇的保留层入口只有两条边。

**第 1 条边：`ui.SduiUiTemplateService → protocol.catalog.DeviceCapabilityProjection`**
- `DevicePrimaryUiService` / `WorkflowUiContextService` **并未**引用投影类（它们只依赖 `section/` 平台 UI 模型），原判断"三个 ui 服务都是入口"是错的。
- 该类对投影的全部使用只有一行 `capabilityProjection.sections(deviceId).forEach(...)` → "设备支持哪些 Section 类型"。
- 改为 `CapabilityQueryService.sectionTypes(deviceId)`（新增方法），读 v2 `CapabilitySchemaV2.surface.ui.sectionTypes`。
- **去掉与平台类型目录求交**：类型存在性已由 `SectionTypeCatalog.isValidType` 在模板创建时校验，下发门禁再求交是第二处真值。v2 的裁决同样是"Section 门禁只认 Schema"（`SectionViewResolver`）。

**第 2 条边：`section.SectionTypeCatalog → event.EventRegistry`**
- 该类 `init()` 里只有 `eventRegistry.getSectionTypes()`——把运行时事件注册表当 YAML 配置读取器用。
- 改依赖 `EventCatalogLoader`（YAML 边界，自身无构造依赖，不成环；`@PostConstruct` 顺序由依赖关系保证，比原 `@Lazy` 代理更可靠）。

**实测**：保留闭包 **39 → 22**，出闭包 17 类（旧能力 14 + 旧事件 3）。**A 类仍 12**——出闭包 ≠ 立即可删，这些类仍被旧协议簇自身引用。

**关键发现**：`SectionTypeCatalog` 不是"ui 的东西"。v2 侧经 `v2.display.SectionViewResolver → section.SectionDataCodec → SectionTypeCatalog` 同样依赖它，而 `SectionDataCodec` 是 v2 硬边界。它是 UI 模型与 v2 **共享的类型定义源**，必须保留；要切的是它的**上游**。

**剩余闭包 22 个**（都是真依赖，不是待清理对象）：平台 UI/Section 模型 12 + 事件目录配置 3（`EventCatalogLoader`/`EventCatalogProperties`/`EventDefinition`）+ 节点目录 6 + TTS 1。`EventDefinition` 仍被 loader 拖着——loader 目前从同一份 YAML 同时构建事件定义与类型条目，要释放它需 P5c 拆 YAML 的 `commands` 与 `sections.types`。

## 引用图新增"阻塞源归因"（`scripts/sdui-refgraph/refgraph.py`）

原"推演后仍留在池中"的说明写作"引用方为 ui / v2，属真实依赖"，解耦后**已失真**：多数滞留类不是被保留方直接引用，而是陷在旧协议簇的内部循环里。循环本身不构成保护，真正要处理的是把循环挂到保留层的**入口**。

新增：从每个滞留类沿**反引用**上溯（限定候选池内），收口到保留层成员，按拖住的类数排序。实测（裁掉 controller/debug 后）：

| 保留层入口 | 拖住 |
| --- | --- |
| `WebSocketConfig` | **56**（接线根的旧端点注册——P5c 主阻塞源） |
| `ui.SduiUiTemplateService` | 14 |
| `ui.DevicePrimaryUiService` / `ui.WorkflowUiContextService` / `v2.display.SectionViewResolver` | 各 11 |
| `v2.display.PrimaryViewPublisher` | 6 |
| `workflow.NodeWorkflowDeploymentService` | 6 |
| `workflow.WorkflowPlatformStepExecutor` | 1 |
| （无保留层入口） | 25（随内部循环一起消失，无需改造） |

这张表直接回答"删这一个能解锁什么"。用"引用数"排序会得到相反结论；用"直接引用者是不是保留包"会把整个内部循环误报成阻塞源。

## 0.14.3 前端调试页面对齐 v2（P5c 5.18 结项）+ 修掉扫描器路径截断

**先排除误判**：三个旧页（`sdui-node-test` / `sdui-workflow-editor` / `sdui-workflow-test`）的每一条调用路径与控制器端点逐一比对，**全部仍然有效**。0.14.0 删的是 `/debug/{id}/command`、`/debug/{id}/commands*`、`/debug/{id}/section*`、`/debug/node-workflows/**`，都是前端从未调用的。旧页没有坏链，只是停在"节点目录驱动"的编排视角，看不到 v2 的能力面与请求面。

**处置：新建 `static/sdui-v2-console.html`，不改造旧三页**。理由：① 视角不同——旧页从节点目录（`CapabilityNodeCatalog`）出发是编排视角，新页从能力 Schema 出发是协议联调视角，后者才是终端对接要的；② 旧三页本身在 P5c 待删清单里，改造即将删除的前端只会留下迁移债；③ 不引入第二处真值——只经能力四端点 / 出站两端点 / 请求目录与历史 / 两条 SSE 取数。

四个页签（能力、请求下发、主视图、实时流），覆盖了此前**无任何调用方**的 v2 调试端点：`POST /debug/{id}/request`、`POST /view`、`GET|DELETE /view/state`、`GET /requests`、`/requests/history`、`/requests/stream`、`/events/stream`。

**修掉 `scripts/sdui-front-paths.py` 的路径截断（重要）**：正则 `[^\s"'`)|]+` 逐字符匹配到右括号即止，而 JS 模板的 `${encodeURIComponent(deviceId)}` 含右括号 → **所有带参数的路径被截成半截**，占位符替换随之失效。危害不是显示难看，而是截断后的路径**无法与控制器端点对账**——"仍在使用的端点"会看起来像没人用，而这正是 §7.2 判断端点存废的依据。修正：① 把 `${...}` 整体作为一个匹配单元；② 新增"路径不是字面量"提示（`api(devicePath('/x'))` 这类辅助函数拼接会静默漏报，必须能被发现）。修正后扫描输出 0 告警。

**项目约定（新增）**：页面的请求路径必须写成完整字面量（模板字面量内部可插值），否则静态扫描看不见。

**顺带发现的文档不一致（已登记为 §4.24）**：§7.3.4 执行顺序第 1 步写"裁三个控制层类"，但其中 `/section-triggers`（契约 §2.3）与 `/telemetry/trends`（契约 §2.1）**都在接口契约内**。§7.2 表里的"真实释放量 2/2/1"是**推演上限**，不是"该删"的结论。结论：5.10.1 当前没有可安全执行的删除动作，应重新裁定为"控制层现有暴露均在契约内，属活功能"；第 1 步实际只剩 `WebSocketConfig` 一项（释放 2 类，且属 P5c 准入）。
